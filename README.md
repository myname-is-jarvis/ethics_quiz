# 행사 퀴즈 설치 순서

구성: `index.html`(정적 페이지, 아무 HTTPS 호스팅) + `Code.gs`(Google Apps Script, 문제·결과는 Google Sheet에 저장)

흐름: QR → index.html → 이름·개인번호·전화·동의 입력 → Apps Script가 시트에서 문제를 랜덤 추출(보기도 셔플) → 답 제출 → 서버 채점 후 Results 시트에 저장 → 점수와 정답 표시 → 전부 정답이면 상품 부스에서 운영자가 "운영자 확인" 버튼으로 지급 처리

## 상품 지급 흐름

1. 참가자가 전부 정답이면 결과 화면에 "축하합니다"와 **운영자 확인** 버튼이 나옵니다.
2. 상품 부스에서 운영자가 참가자 휴대폰의 버튼을 누릅니다. 서버가 `Results`의 `claimed=Y`, `claimed_at`을 기록하고 화면이 "지급 완료 + 시각"으로 바뀝니다.
3. 같은 번호로 다시 누르면 서버가 `already_claimed`를 돌려주고 화면에 "이미 지급된 건입니다"가 나옵니다. 캡처 화면에는 버튼이 있어도 서버 기록이 없으면 지급 전이고, 기록이 있으면 화면이 "지급 완료"로만 나옵니다.
4. 페이지를 닫았던 참가자는 첫 화면에서 같은 이름·번호를 입력하면 "이미 참여한 번호" 안내와 함께 **내 결과 보기** 버튼이 나오고, 이름이 저장값과 일치할 때만 결과·지급 상태를 다시 볼 수 있습니다.
5. `Code.gs`의 `STAFF_PIN`에 값을 넣으면 운영자 확인 시 PIN을 물어봅니다. 참가자가 스스로 버튼을 눌러 버리는 실수를 막을 수 있으므로 설정을 권합니다. PIN은 참가자 휴대폰에 입력하게 되므로 행사 중 유출될 수 있고, 유출돼도 본인 상품을 스스로 소진하는 것 외의 피해는 없습니다.

개인번호는 `emp_id` 열(M)에 저장되며 `0000`은 외부인으로 집계됩니다. 운영자가 시트에서 직접 `claimed`에 `Y`를 입력해도 동일하게 동작합니다.

## 설치

1. Google Sheet를 새로 만들고 `확장 프로그램 > Apps Script`를 엽니다. 기본 코드를 지우고 `Code.gs` 내용을 붙여넣고 저장합니다.
2. 함수 선택에서 `setupSheets`를 실행하고 권한을 승인합니다. `Questions`, `Results` 시트가 생깁니다.
3. `Questions` 시트에 문제를 입력합니다. 열은 1행의 헤더 이름(`id, question, opt1, opt2, opt3, answer, active, hint`)으로 찾으므로 열 순서는 자유이고, `opt4` 열을 두면 4지선다도 됩니다.
   - `id`는 유일해야 합니다 (중복되면 채점이 꼬입니다).
   - 한 문제 안에서 보기 텍스트가 서로 달라야 합니다 (텍스트로 채점).
   - `answer`는 정답 보기 번호(1~3), 보기는 2~3개. O/X 문제는 `opt1`=O, `opt2`=X, `opt3`은 비우고 `answer`에 1 또는 2. 보기가 2개인 문제는 순서를 섞지 않고 좌우로 크게 표시합니다(`SHUFFLE_TWO_OPTIONS`).
   - `hint`에 글을 넣으면 그 문제에 "힌트 보기" 버튼이 생깁니다. 비우면 버튼이 없습니다.
   - 출제 구성은 `Code.gs`의 `QUIZ_MIX`로 정합니다. 기본값은 보기 2개(O/X) 1문제 + 보기 3개 1문제이며, 이 순서로 출제됩니다. 문제는 `id`가 아니라 보기 개수로 분류되므로, 보기 4개짜리 문제는 이 구성에서는 출제되지 않습니다. `QUIZ_MIX`를 `[]`로 두면 전체 활성 문제에서 무작위로 뽑습니다.
   - 이전 버전 시트(`opt4` 열 포함)는 그대로 써도 됩니다. `opt4` 열을 지우려면 `answer`가 4인 문제가 없는지 먼저 확인하세요.
   - `active`에 `N`을 넣으면 출제에서 빠집니다. 재배포 없이 즉시 반영됩니다.
   - "위의 모두", "①과 ③" 같은 순서 의존 보기는 쓰지 마세요 (보기가 셔플됩니다).
4. `testQuestions`를 실행해 실행 로그에 10문제 JSON이 찍히는지 확인합니다.
5. `배포 > 새 배포` → 유형 **웹 앱** / 실행 사용자 **나** / 액세스 권한 **모든 사용자** → 배포 → 웹 앱 URL 복사.
6. `index.html`의 `API_URL`을 그 URL로 바꾸고, `EVENT_TITLE`과 개인정보 고지 문구(`[확인 필요]`)를 수정합니다.
7. `index.html`을 GitHub Pages, Netlify, Cloudflare Pages 등 HTTPS 호스팅에 올리고, 그 주소로 QR을 만듭니다.
8. 실제 휴대폰으로 처음부터 끝까지 한 번 진행해 `Results`에 행이 추가되는지 확인한 뒤 테스트 행을 지웁니다.

## 동시접속 대응 (v2)

- 문제 pool과 참여 번호 목록을 CacheService에 60초 캐시합니다. Questions 시트를 고친 뒤 바로 반영하려면 편집기에서 `clearCache`를 실행합니다. Results에서 테스트 행을 지운 뒤에도 `clearCache`를 실행하세요.
- 제출 잠금 구간은 중복 검사와 행 추가만이며, 잠금 대기가 5초를 넘으면 `busy`를 돌려줍니다. 페이지는 `busy`, 할당량 초과(HTML 응답), 네트워크 오류에 대해 최대 5회 자동 재시도합니다(1.5초부터 2배씩, ±50% 지터).
- 제출마다 `token`을 저장합니다. 응답이 유실되어 페이지가 재시도하면 같은 token이므로 중복이 아니라 이전 결과를 다시 돌려줍니다.
- 시작 시 중복 검사는 캐시 기반이라 최대 60초 늦을 수 있고, 제출 시 검사는 시트를 직접 읽어 확정합니다. `buildStats`는 같은 번호의 두 번째 이후 행을 제외하고 집계합니다.
- 바꿀 수 없는 한도: Apps Script 동시 실행 30개/사용자. 수백 명이 같은 순간에 제출하는 상황이면 백엔드를 Supabase/Firebase로 옮겨야 합니다.

## 통계

Apps Script 편집기에서 `buildStats`를 실행하면 `Stats` 시트가 만들어지거나 갱신됩니다.
참여자 수(내부/외부), 중복 제외 행 수, 평균 점수, 상품 대상자 수와 지급/미지급 수, 점수 분포, 문제별 출제 횟수·정답률, 상품 대상자 명단(이름·개인번호·전화번호·지급 시각)이 들어갑니다.

 행사 중에도 반복 실행할 수 있습니다.

## 주의

- `Code.gs`를 고친 뒤에는 `배포 관리 > 새 버전`으로 다시 배포해야 반영됩니다.
- 이전 버전의 `Results` 시트가 있으면 `setupSheets`를 한 번 더 실행하세요. 열 헤더(`token`, `claimed`, `claimed_at`, `emp_id`)를 채우고 C·M열을 텍스트 서식으로 바꿉니다. 기존 행은 그대로 유지됩니다.
- 전화번호는 `010-1234-5678` 형태의 텍스트로 저장되며, 예전에 숫자로 저장돼 앞자리 0이 빠진 행도 같은 번호로 비교합니다.
- 중복 참여는 전화번호 기준으로 막습니다. 허용하려면 `CONFIG.ALLOW_DUPLICATE_PHONE = true`.
- 정답은 제출 전에 브라우저로 내려가지 않고 서버에서만 채점합니다.
- 이름·전화번호를 수집하므로 개인정보 수집·이용 동의 문구(항목, 목적, 보유기간, 거부권)는 담당자 확인이 필요합니다.

## 실제 배포 환경에서 검증하지 못한 부분

- Apps Script 웹앱의 동시 실행 한도 수치. 참여가 행사 중 분산된다면 문제 될 가능성은 낮다고 판단하지만, 확인된 수치는 아닙니다.
- 브라우저 `fetch` → Apps Script `POST`(`text/plain` 전송, 리다이렉트 후 응답 읽기)는 널리 쓰이는 패턴이지만, 반드시 실제 휴대폰에서 8번 항목대로 테스트하세요.
- 백엔드 로직(랜덤 추출, 비활성 제외, 채점, 중복 차단, 통계)은 Apps Script 서비스를 흉내 낸 로컬 테스트로만 확인했습니다.
